## 3. HTTP parity

### 3.1 Normaliser (`backend-rs/tools/parity`)

- Replace by first-occurrence placeholders: UUID v4/v7, ISO timestamps, request ids, JWTs, LSNs (`[0-9A-F]+/[0-9A-F]+`),
  generated references (configurable regexes per route), `webhook-id`/`webhook-timestamp`.
- Ignore `details[].message` unless the route's fixture pins it.
- Key order is significant; header comparison limited to an allowlist (`content-type`, `content-disposition`,
  `cache-control`, `x-pg-*`, `x-content-sha256`, `ratelimit-*`, `retry-after`, `location`, `set-cookie` attributes).

### 3.2 Edges

The existing edge suites boot `createApp` in-process with a fake mTLS core (`test/helpers/upstream.ts`). Add a launcher:
when `EDGE_UNDER_TEST=rs`, the suite spawns the Rust edge binary configured against the same fake upstream and runs
the same assertions over HTTP. White-box tests (pool selection, env parsing, limiters) are rewritten as Rust unit tests.

### 3.3 Core reads

- **Replay suite**: a fixed database (COMPACT synthetic seed restored from a committed `pg_dump`), a generated request
  list per GET route (`tests/parity-fixtures/reads/*.yaml`: path params from seed data, representative filters,
  pagination, both principals where applicable), executed against TS and Rust, diffs reported per route.
- **Shadow mode** in staging (§6.2) for ≥ 48 h before a route switches.

### 3.4 Core writes (dual-database replay)

- Restore the same dump into databases A (TS) and B (Rust); run the same scripted scenario
  (`tests/parity-fixtures/writes/<group>.yaml`: ordered requests with captured variables, e.g. created ids) against
  each implementation.
- Compare: normalised responses, then a **semantic DB diff**: per table, rows keyed by business keys (configured per
  table, e.g. attempts by `(link_id, idempotency_key)`), ids/timestamps/hashes normalised, JSON compared after JS key
  ordering; ledger balances per account must be exactly equal; audit rows compared by `(action, entity_type, actor)`;
  outbox payloads compared after normalisation.
- Workers run in both environments with identical worker sets during the scenario (or are disabled and ticked
  explicitly by the scenario through a test-only admin hook in both implementations — the hook is compiled only in
  test builds).

### 3.5 `PARITY.md`

Generated table: route, method, TS origin, policy, status (`not-started | ported | replay-green | shadow | live-rs |
deferred`), last diff count, notes.

## 4. Porting tests

- For each ported module, port its TS tests first (red), then implement (green). Keep test names for traceability.
- DB-backed tests use PostgreSQL 18 + Redis (same env names as TS suites: `DATABASE_URL`, `STORAGE_TEST_REDIS_URL`);
  `testcontainers` for local runs, CI service containers otherwise. Suites must **fail**, not skip, when the database
  is missing (fixes the silent-skip problem, GAP-014).
- Track the ported-assertion count per module in `PARITY.md` (TS had ~23k assertions in core, 2026-11-08).

## 5. Property tests and fuzzing

- Ledger: templates balance after folding; shard routing in range; `shard_seq` gapless under concurrency; checkpoint
  proof holds after random posting sequences; rounding error ≤ 0.0001 per leg.
- Flow: random event sequences never produce a transition outside `ALLOWED_TRANSITIONS`; slots never exceed
  `use_count` under concurrent confirms.
- Transforms: random inputs equal golden behaviour (differential against a TS oracle process in CI for 10k cases).
- Fuzz targets: chapter 5 §8.

## 6. Coexistence and cutover

### 6.1 Topology during Track P

Each core node runs TS core (4000/4005) and Rust core (4010/4015) with the same certificates and databases. Edges
(Rust from P2) hold two pools: `ts` (`CORE_BACK_URLS`) and `rs` (`CORE_RS_BACK_URLS`), plus sandbox equivalents.

### 6.2 Route table (`pg-upstream`)

```yaml
version: 1
default: ts                       # ts | rs
pools:
  ts: { urls_env: CORE_BACK_URLS, sandbox_urls_env: SANDBOX_CORE_BACK_URLS }
  rs: { urls_env: CORE_RS_BACK_URLS, sandbox_urls_env: SANDBOX_CORE_RS_BACK_URLS }
routes:
  - match: { method: GET, pattern: "/internal/merchant/payments" }
    target: rs
  - match: { method: GET, pattern: "/internal/merchant/links/:id" }
    target: shadow
    shadow_percent: 100
  - match: { method: POST, pattern: "/internal/checkout/pay/:linkKey/confirm" }
    target: rs
    fallback: none                # writes never fall back
```

- Patterns use the inventory syntax; matched after path normalisation; first match wins; unmatched → `default`.
- `shadow` (GET/HEAD only): serve TS, mirror to Rust asynchronously, diff normalised responses, write diffs to
  `SHADOW_DIFF_PATH` (bounded JSONL) and a metric; mirrored requests carry `x-pg-shadow: 1` and Rust must not perform
  side effects for them (GETs are side-effect free except access logs, which are suppressed for shadow requests).
- Reads may declare `fallback: ts` (default for GET); writes never fall back (fail closed with
  `503 CORE_UNAVAILABLE`) to avoid double execution.
- Hot reload on SIGHUP; `pgctl route-table set/push` manages it; every change is logged with the operator identity.

### 6.3 Worker hand-off

- TS: `WORKER_DISABLED` (P0-T03). Rust: `WORKER_ENABLED_LIST`.
- Singleton procedure: enable in Rust → both contend for `hashtextextended('worker:'||name, 0)` → disable in TS →
  confirm Rust leads in `/health.workers` → watch worker-specific invariants for 72 h.
- Queue workers (SKIP LOCKED) may run in both during overlap.
- Rollback: re-enable in TS, disable in Rust (`pgctl workers handover <name> --to ts`).

### 6.4 Implementation switches

| Component | Switch | Rollback |
| :--- | :--- | :--- |
| Each edge | `services.<edge>.impl = ts|rs` | set back, `pgctl apply --only <edge>` |
| Core routes | route table | `pgctl route-table set <route> ts` |
| Workers | lists | `pgctl workers handover` |
| Daemons | `services.<daemon>.impl` | same as edges |
| Migrations owner | `db.migrator = prisma|core-rs` (P10-T01) | back to prisma until P10 gate |

### 6.5 Cutover runbook per route group (template)

1. Parity replay green; PR merged; release deployed with the route still `ts`.
2. Set `shadow` in staging; 48 h with zero diffs (or diffs explained and fixed).
3. Set `rs` in staging; run BL-3/BL-5 subsets and the live journeys; 24 h observation.
4. Production: `shadow` 24 h → `rs` during business-low hours with an operator watching dashboards; watch window 2 h.
5. Record in `PARITY.md` and TRACKER.

### 6.6 Final cutover (P10)

- All routes `rs`, all workers Rust for 7 days in production without rollback → TS core stopped (kept installed
  for 30 days) → Rust core moves to ports 4000/4005 via a pgctl release that updates edge pools → TS removal (P10-T09).

## 7. Benchmarks

### 7.1 Environments

- **B-local**: one 8-core machine (PostgreSQL 18 + PgBouncer + Redis local) for relative comparisons.
- **B-lab**: `pgctl lab` topologies single-host, split, replicated (and `ha` after D5) on fixed hardware; TS and Rust

### 7.3 Reporting (`BENCHMARKS.md`, append-only)

Per run: date, git commit, implementation, hardware, topology, preset, database size, configuration diffs, results
table, delta vs TS baseline and vs targets, flamegraph links (`perf record -g` + `inferno`) for any regression.

### 7.4 Targets

| ID | Target |
| :--- | :--- |
| S1 | ≥ 4,500 postings/s on one core node (then DB-bound) |
| S2 | ≤ 1.0 ms application CPU per posting |
| S3 | ≥ 2,000 checkout initiate TPS at p95 < 35 ms (certification preset hardware) |
| S4 | edge added latency ≤ 0.3 ms p50, ≤ 1.5 ms p99 |
| S5 | RSS per process ≤ 35% of TS at the same load |
| S6 | RSS growth < 5% after the first hour of a 72 h soak; zero FD growth |
| S7 | zero unexpected 5xx during soak and chaos; invariants green |
| S8 | 100% route parity; zero open parity diffs |

A missed target is profiled and either fixed or explicitly accepted by the owner in TRACKER.

## 8. Certification (P10-T06)

1. All S1–S8 measured on B-lab.
2. **72 h soak** at 60% of measured Rust max TPS with a realistic mix (checkout initiate/confirm/callbacks, merchant and
   admin reads, webhooks, all workers), hourly invariant checks.
3. **Chaos suite**: PostgreSQL primary connection kills and restart; Patroni switchover (HA topology); Redis down 2 min
   (velocity policy behaviour per `REDIS_VELOCITY_FAILURE_POLICY`); 500 ms replica lag; kill a core node under load;
   object-storage disk full; certificate rotation with hot reload; network partition between edge and core; clock skew
   alarm. Pass: no ledger drift, no double posting, every in-flight attempt ends defined, no crash loops.
4. **Backup/restore drills**: pg-native full + PITR restore of a Rust-produced backup; restore of a TS-produced backup by
   the Rust daemon and vice versa; object-storage parity drill on a live two-host setup (closes GAP-067/077 evidence).
5. **Security**: IDOR matrix, TLS negative tests, secrets-in-logs scan, dependency audit clean, external pentest report.
6. **Deploy**: fresh, update, rolling, rollback, zero-downtime single node, firewall verification, PKI rotation in the lab.

## 9. Invariant gates (after every benchmark, soak, chaos, parity write run and migration)

- System equation drift = 0 (`InvariantVerifier`).
- Every shard checkpoint proof green (gapless count, parity).
- `verify_audit_chain()` true; anchors verify.
- Slot counters consistent (ConsistencyAuditWorker query).
- No parked outbox rows created by the run; no rows in DEFAULT partitions.
- Background job queue drained; no stuck leases.
