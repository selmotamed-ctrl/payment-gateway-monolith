# Smart AI Spec Importer and Voucher Half (Future)

## 1. Purpose and scope

This part documents the Smart AI-assisted onboarding pattern and its two intended applications:

- **Payment gateway rails:** implemented in `core-back/engine/specImporter/**` and `admin-front/src/pages/gateways/ai-import/index.tsx`.
- **Voucher providers:** designed but absent.

The overall feature is partial: the gateway half works, the voucher half is missing. This part has frontmatter status `missing` because the voucher half is the subject and it does not exist. The gateway half is described as current evidence and as the reusable specification pattern.

## 2. Design intent (extracted and synthesized from ./design)

### 2.1 The BYO-AI workflow

Manually filling an eight-step gateway wizard or building a multi-query voucher stack from a PDF or Postman collection is slow and error-prone. Plugging an external LLM into the backend would violate the air-gapped/LAN security boundary and risk sending live credentials to a third party.

The design uses an offline "Bring-Your-Own-AI" workflow:

1. **Download the AI onboarding kit.** The admin downloads a self-contained Markdown transcript generated by the backend from the live schema. It contains role instructions, the exact JSON schema, closed lists of auth methods/parameter sources/transforms/crypto operations, two gold-standard examples, and a fill-in section for the provider docs and credential names.
2. **Generate the spec externally.** The admin gives the transcript plus the provider documentation and credential field names to any external AI. The AI outputs one strict `integration-spec.json` with embedded `test_vectors`.
3. **Upload and verify.** The backend runs a four-layer verification before writing anything:
   - Layer 1: JSON/Zod schema and `spec_version`.
   - Layer 2: semantic and security guard (HTTPS, no private/loopback SSRF, no `PREVIOUS_REQUEST_DATA` on step 1, `MOVES_MONEY` retry policy `NEVER`, type-safe selectors/transforms).
   - Layer 3: offline vector simulation of request builders, crypto signers and response extractors against the embedded vectors.
   - Layer 4: collision check for gateway/provider/rail code.
4. **Bind secrets and activate.** Verification returns `requiredCredentials`. The UI renders password inputs for those keys. Import writes the full configuration in one transaction as a draft/blocked record, then the admin runs the live credential check or API-listing test and promotes it through maker-checker (gateway) or unblock (voucher).

### 2.2 Three refinements

- **Credential shape vs actual secrets.** The transcript must instruct the AI to use credential names/types or dummy sandbox values, never live secrets. The spec declares `required_credentials` (for example `[{ key: "MID", is_secret: false }, { key: "MerchantSecretKey", is_secret: true, encoding: "HEX" }]`). The portal collects the real values.
- **Embedded self-test vectors.** The AI must extract 2-3 sample request/response payloads from the provider docs into `test_vectors`. The backend simulates them before any live call and returns an `aiRepairPrompt` on failure.
- **Always import as draft/blocked first.** The spec creates a `DRAFT` gateway version or a `blocked=true` voucher provider. Activation is a separate, verified step.

### 2.3 Spec differences between the two systems

| Spec section | Payment gateway | Voucher system |
| :--- | :--- | :--- |
| Identity | gateway code/name/operator/country/aliases/kind; SANDBOX/LIVE URLs and allowed hosts | provider name/base URL; provider meta rows |
| Auth | `gateway_auth` (ten methods) plus credential manifest, owner type and settlement target | auth method (`NONE`, `PERMANENT_TOKEN`, `REFRESH_TOKEN`, `USERNAME_PASSWORD`, `BASIC_AUTH`), auth apply, credential manifest |
| Catalog | rail code, bilingual name, collection mode, capabilities, rail fields, rail route limits/cost model | service link, `FIXED` products or `API` listing config with list/amount/price/face-value selectors |
| Execution | crypto profiles, flows across ten phases with `TransformPipe[]`, confirmation channels, status rules, error maps | purchase query stack with ordered queries, parameters, success checks and extraction |
| Vectors | sample initiate/confirm/webhook payloads, expected canonical status, signature string and wire amount | sample API-listing and purchase responses, expected extracted secret/serial/price |

### 2.4 Five reusable milestones

1. Unified spec Zod schema and cross-field semantic validator.
2. Dynamic AI transcript generator from live enums, transform whitelist and examples.
3. Offline vector simulator and dry-run verifier.
4. Atomic spec materializer.
5. Admin portal smart-AI wizard.

## 3. As-built architecture

### 3.1 Gateway half (implemented)

`core-back/engine/specImporter/` contains:

- `specSchema.ts`: the Zod spec schema, enums and inferred types.
- `specValidator.ts`: schema, semantic, SSRF, retry, selector and crypto-reference checks.
- `SpecSimulator.ts`: offline vector simulation and verification report.
- `SpecMaterializer.ts`: atomic transactional import into draft gateway configuration.
- `TranscriptBuilder.ts`: dynamic Markdown kit generation.
- `index.ts`: public exports.

Admin routes in `core-back/api/internal/admin.ts`:

- `GET /gateways/ai-transcript`
- `POST /gateways/spec-verify`
- `POST /gateways/spec-import`

Admin UI:

- `admin-front/src/pages/gateways/ai-import/index.tsx`
- URL map entries `gatewayAiTranscript`, `gatewaySpecVerify`, `gatewaySpecImport`.
- The current admin guide (Book 6) documents the download -> external AI -> upload -> four-layer verification -> secret binding flow.

Tests:

- `core-back/test/spec-importer.test.ts` covers schema defaults, unknown auth methods, wrong version, transform list parity, SSRF, host allowlists, first-step `PREVIOUS_RESPONSE`, `MOVES_MONEY` retry, unknown crypto/placeholder, weak inbound channel, missing vectors, unimportable step types, aggregated defects, golden spec, initiate vector, wrong extraction/status/wire amount, signature vector, Layer 4 collision, self-contained kit, tailored examples and the secret warning.
- `core-back/test/spec-materializer.test.ts` covers draft import in one transaction, `NEW_VERSION`, duplicate `CREATE_NEW` refusal and invalid spec refusal.

The gateway half is real. It is the model to copy, not a voucher implementation.

### 3.2 Voucher half (missing)

There is no:

- `back/lib/specImporter/**` or equivalent voucher module.
- Voucher spec schema, validator, simulator, materializer or transcript.
- `POST /api/admin/providers/spec-verify` or `spec-import`.
- `front/src/pages/providers/ai-import`.
- Voucher database, provider registry or query engine.
- Voucher tests.

The voucher design therefore remains a specification. It must not be described as current.

### 3.3 Why the pattern is reusable

The gateway importer separates five concerns cleanly:

1. **Schema** (`specSchema.ts`) is independent of the UI and route layer.
2. **Semantics** (`specValidator.ts`) returns structured, AI-friendly diagnostics with `{path, code, message, aiFixHint}`.
3. **Simulation** (`SpecSimulator.ts`) executes request builders, transforms, signers and extractors in memory against `test_vectors`. It needs no network.
4. **Materialisation** (`SpecMaterializer.ts`) re-runs verification inside the backend, encrypts secrets and writes one transaction.
5. **Transcript** (`TranscriptBuilder.ts`) is generated from the live schema so the closed lists cannot drift.

A voucher port would keep those five boundaries and replace the inner domain payload:

- Identity: provider name, base URL, meta.
- Auth: five voucher methods and `auth_apply`.
- Execution: ordered purchase queries, place/type/key/selector/constant parameters, success checks and extraction.
- Catalog: service link source `FIXED` or `API`, listing selectors, product meta and purchase parameters.
- Vectors: sample listing and purchase responses with expected extraction.

The shared concerns (credential manifest, SSRF guard, secret redaction, offline simulation, atomic materialisation, repair prompt) should be extracted rather than copied blindly. The design says the architecture, UI flow and verification pipeline are about 90 percent identical.

## 4. Contracts and invariants (future voucher half)

1. The voucher spec version is explicit and checked.
2. URLs are absolute HTTPS and pass the same private/loopback/metadata SSRF guard.
3. `PREVIOUS_REQUEST_DATA` is invalid on the first query.
4. A purchase query that may move money is never retried automatically.
5. Selectors and recursive-set keys use a safe dot-path grammar; `__proto__`, `constructor` and `prototype` are rejected.
6. Auth methods are a closed list; `AUTH_TOKEN` listing parameters require a token-producing auth method.
7. `required_credentials` contains names and shapes only, never values.
8. Import is atomic and creates a blocked provider.
9. Verification runs again inside the backend during import.
10. Secrets are encrypted with the Vault before persistence and redacted from logs.
11. The transcript is generated from live enums and the actual transform/parameter whitelist.
12. Every vector must execute offline; a failing vector returns a copyable repair prompt.

## 6. Operational usage

For the gateway half:

1. Open `/gateways/ai-import`.
2. Download the AI onboarding transcript.
3. Give the transcript and partner docs to an external AI. Never include live secrets.
4. Upload `integration-spec.json` and run verification.
5. If a layer fails, copy the repair prompt back to the AI.
6. Bind the declared credentials.
7. Import as draft and run the live credential check.

For the voucher half: not applicable; no component exists.

## 7. Status and deviations

### Implemented (gateway half)

- Spec schema, semantic/SSRF validator, offline simulator, atomic materializer, transcript builder.
- Three internal admin routes and the admin UI page.
- Tests for the golden spec and failure paths.

### Partial

- The reusable pattern is not extracted into a shared module; a voucher port would duplicate code unless refactored.
- The current transcript/examples are gateway-specific.

### Missing / deferred (voucher half)

- Everything listed in section 3.2.
- A shared `specImporter` package usable by both systems.
- A voucher transcript with provider/auth/query/listing/extraction examples.
- A voucher simulator for listing and purchase vectors.
- A voucher materializer and admin wizard.
- Voucher tests.

### Known bugs / risks

- **Documentation risk:** the existence of the gateway importer may be misread as the voucher feature existing.
- **Duplication risk:** copying the gateway module without extracting shared guards would create two security implementations.
- **Secret risk:** an AI transcript that includes real credentials would leak them to a third-party model.
- **Drift risk:** a hand-written voucher transcript would fall out of sync with the live schema.

## 8. Verification and tests

Gateway half:

- `core-back/test/spec-importer.test.ts` (about 29 declarations) covers schema, semantics, SSRF, vectors and transcript.
- `core-back/test/spec-materializer.test.ts` (4 declarations) covers atomic import and collision/version behaviour.

Voucher half: none. Acceptance requires the voucher module, routes, UI, schema, simulator, materializer and a test suite mirroring the gateway coverage plus voucher-specific listing/purchase/extraction vectors.
