# Platform Overview

## 1. Purpose and scope

The repository is a multi-rail payment gateway and payment-links platform built around a single database-owning core service. It lets an operator add a gateway by declarative configuration instead of a code release, lets a merchant create payment links and onboard through KYB/AML, and lets an anonymous payer complete a payment through one of the visible rails and collection modes.

This part owns the product-level overview: the workspaces, product scope, the seven-service topology plus the optional Fake Rails tier, the implemented versus unimplemented capabilities, and the lineage from the historical design corpus to the current code. It does not own the detailed contracts of the core API, the rail engine, the ledger, storage, deploy or any individual frontend; those are owned by the later parts.

The primary users are:

- Platform operators in the admin back office: onboarding review, KYB, AML, approvals, gateways/rails/routes, reconciliation, finance, disputes and backups.
- Merchants and merchant staff in the merchant portal and through the external `pg_live_` server API: onboarding, wallets, applications, links, POS, payments, disputes, cash-outs, tokens and credentials.
- Anonymous payers on the hosted checkout: link resolution, rail selection, customer fields, OTP/redirect/embedded/QR/push flows and status polling.
- Internal edge services, which are not human users but callers whose identity is a client certificate common name.

## 2. Design intent (extracted and synthesized from ./design)

The historical corpus describes a national payment switch for the Libyan market with a first-party wallet rail, plus direct and aggregator integrations for the roughly twenty researched gateways. The product is not a simple redirect wrapper: the customer is in the loop, confirmations arrive late, twice, through a browser or through a statement, and money may settle days after the payment attempt. The design therefore adds a declarative flow engine, an attempt state machine, a trusted-confirmation layer and an ownership-aware double-entry ledger on top of the voucher-style provider pattern.

The stable design intent, corrected where the code has moved on, is:

1. **Four catalog layers.** A `Gateway` is one technical integration. A `CredentialSet` is whose account and secrets are used, per environment, with an ownership and settlement target. A `Rail` is what the customer sees and chooses. A `Route` binds a rail to a gateway through a credential set with priority, cost, limits, health and scope.
2. **Two independent axes.** Collection mode is what the customer does: `OTP_PULL`, `REDIRECT`, `EMBEDDED`, `PUSH_APPROVAL`, `QR_DISPLAY`, `PAY_CODE`, `DEEP_LINK`, `MANUAL`, `HYBRID`. Confirmation channel is how the platform learns the result: sync response, webhook, inquiry/poll, return URL, browser callback, statement, operator confirmation.
3. **Zero-trust split.** `core-back` is the only service with database credentials, the KMS master key, ledger-posting authority and outbound gateway execution. The edge backends have no database drivers or credentials and call core only over mutual TLS.
4. **Declarative engine plus escape hatch.** The engine supports a closed transform library and declarative phases. A native adapter is the escape hatch for proprietary protocols, but it still goes through the same attempt state machine, inbox, verifier and ledger poster.
5. **Nothing browser-side is trusted.** Widget callbacks and return URLs are hints that trigger a server inquiry. Money is posted only after the trusted-success facts match.
6. **Immutable configuration.** Gateway versions are snapshots; an attempt pins its gateway version, route, credential set and commission profile at creation.
7. **Uncertain outcomes become `UNKNOWN`.** A timeout, reset, 5xx or extraction failure on a money-moving step is not retried blindly.
8. **Ownership-aware ledger.** Platform-held settlement uses gateway clearing accounts; merchant-direct settlement books commission only; internal rails clear through treasury.
9. **Governance and compliance.** Maker-checker, KYB, beneficial-owner screening, AML rules, confidential AML access, disputes, adjustments, cash-outs, reconciliation and reporting are part of the product, not add-ons.
10. **Operational safety.** Durable workers, a webhook inbox, statement reconciliation, backups/PITR drills, and horizontal deployment are part of the architecture.

The target scale stated in the historical design is a national switch with tens to hundreds of millions of records, `1..N` compute nodes per tier, `0..N` PostgreSQL streaming replicas, PgBouncer in transaction mode, Redis for cache/velocity, dedicated audit and log databases, and 5 to 30+ dedicated hosts. The code supports the horizontal arrays and the storage ports; no production-shaped scale run is recorded in the repository.

## 3. As-built architecture

The workspace contains four backend services, three Vue 3 + Vuetify 3 + TypeScript frontends, an optional Fake Payment Rails emulator (backend and portal), a deployment engine with a backup daemon, tests and the canonical design tree.

| Workspace | Runtime | Role | Evidence |
| :--- | :--- | :--- | :--- |
| `core-back` | Bun + Express 5 + native TLS server | PostgreSQL owner, domain engine, ledger, governance, workers, backup control client, synthetic seeder | `core-back/index.ts`, `core-back/api/**`, `core-back/engine/**`, `core-back/lib/**` |
| `admin-back` | Bun + Express 5 | LAN-only admin edge BFF; validates and forwards to `/internal/admin/*` | `admin-back/index.ts`, `admin-back/api/**`, `admin-back/lib/coreInternalClient.ts` |
| `merchant-back` | Bun + Express 5 | Public merchant portal API and external `pg_live_` API; forwards to `/internal/merchant/*` | `merchant-back/index.ts`, `merchant-back/api/**` |

| `merchant-front` | Vue 3 + Vuetify 3 + Vite | Merchant portal SPA | `merchant-front/package.json`, `merchant-front/src/**` |

| `tests` | Playwright/Vitest | Cross-workspace and live-stack journeys | `tests/**` |

The seven-service topology is therefore `core-back`, the three edge backends and the three frontends. Fake Rails is an eighth and ninth workspace only when enabled. The core is private-LAN only on port `4000`; the admin edge listens on `4101` and is normally reached through a LAN-only nginx vhost on `8443`; merchant and checkout edge backends listen on `4102`/`4103` behind public TLS reverse proxies. Ports are deployment-configured, with the defaults above in the deploy schema.

The product scope implemented in code includes:

- Payment links with single-use and multi-use slots, link cancellation, visible rails and fee breakdowns.
- A universal rail engine with seven runtime phases, a separate credential-check phase, 39 transforms, crypto profiles and a scoped SSRF guard.
- A PostgreSQL 18 schema with 75 models and 105 enums at schema version 9, and five migrations: baseline, storage engine, CQRS read models, storage hardening and the 2026-11-04 DB read/write optimisation.
- A double-entry ledger, 17 `LedgerScenario` values and 11 GL account types, with sharded system GL accounts.
- Merchant onboarding, KYB documents, beneficial owners, screening, AML rules/cases, regulatory reports, disputes, adjustments, cash-outs and reconciliation.
- Admin and merchant authentication with password login, optional MFA challenge, session JWTs and merchant `pg_live_` API tokens.
- Admin maker-checker approvals, with the executable-handler coverage described in `01-core-back/01-api-surface.md`.
- Durable workers for expiry, polling, inbound inbox, notification outbox, ledger invariants, join-request expiry, periodic screening, KYB expiry, retention and the background job queue.
- Storage engine ports for unit-of-work, replica reads, Redis cache/velocity, dedicated audit and dedicated logs.
- Backup control through the mTLS `pg-backup-daemon`, with catalog, trigger, drill and policy routes.
- Optional Fake Rails emulator and tester portal.
- Deploy engine with horizontal compute/storage node arrays, PKI, firewall, nginx/PM2 templates and ordered pipeline.

The product scope intentionally not implemented is tracked in section 7 and in `project-design/appendices/stale-claims-register.md`. In particular, the voucher provider system exists only as design, guide v2 is future work, Google OIDC is a 501 stub, and `CAPTURE`/`SETTLEMENT_FETCH` are reserved enum values.

## 4. Contracts and invariants

The platform-level non-negotiables are:

1. **PostgreSQL 18 is the only runtime database.** The Prisma datasource is `provider = "postgresql"`; the runtime uses `@prisma/adapter-pg` and `pg`; `DATABASE_URL`, replica URLs, audit and log URLs are validated as PostgreSQL URLs in `core-back/lib/env/index.ts`. MySQL and MariaDB support have been removed.
2. **Money is decimal.** Runtime money uses `Decimal`/`decimal.js` and Prisma `NUMERIC(18,4)`; the transform library forbids `to_number` on monetary outputs.
3. **Database exclusivity.** Only `core-back` holds `DATABASE_URL`, database drivers, `KMS_MASTER_KEY`, ledger authority and outbound gateway credentials. Edge backends' package manifests and environment schemas contain no database driver or database URL; their only upstream is `CORE_BACK_URL` / `CORE_BACK_URLS`.
4. **mTLS and channel identity.** `core-back` requires a client certificate signed by the internal CA and binds each internal namespace to one common name: `/internal/admin/*` only `admin-back`, `/internal/merchant/*` only `merchant-back`, `/internal/checkout/*` only `checkout-back`.
5. **Authorities are enforced by core.** Edge checks are advisory. `core-back` re-authenticates the bearer credential, re-reads the user/merchant/authority state from the database, and re-validates payloads.
6. **Maker-checker is server-side.** The approval route and governance execution require a human user, a checker authority, and a checker different from the maker; the database also has a check constraint and a trigger on `approval_requests`.
7. **Atomic critical writes.** The ledger, outbox and audit outbox are written in one transaction on the critical path; the storage engine's `UnitOfWork` owns the commit LSN.
8. **Secrets and confidential data never reach logs.** Vault redaction covers sensitive field names, literal decrypted secrets and Luhn-valid PANs. Edge services never receive the KMS key or database credentials.
9. **Bilingual catalogues stay in sync.** User-facing text is maintained in English and Arabic.
10. **Deploy-time UI flags are runtime-controlled.** The deploy engine writes `showChecklists`/`showSnapshotExportChecklist` and `showHelpPanels` into the admin runtime config and injects the matching `VITE_*` build constants; source builds fall back to the documented defaults.

## 5. Data / API / config / deployment surface

The platform surface is split by trust boundary:

- **Human frontends:** `admin-front` calls `admin-back`; `merchant-front` calls `merchant-back`; `checkout-front` calls `checkout-back`. None of them calls core directly.
- **Edge HTTP surfaces:**
  - Admin edge: `/api/v1/admin/*` (auth routes plus protected router).
  - Merchant edge: `/api/v1/merchant/auth/*`, `/api/v1/merchant/onboarding/*`, `/api/v1/merchant/*`, `/api/v1/external/*`.
  - Checkout edge: `/api/v1/pay/*`, `/api/v1/return/*`, `/api/v1/inbound/*`.
- **Core internal surfaces:** `/internal/admin/*`, `/internal/merchant/*`, `/internal/checkout/*`, plus an `/api/public` mount with a rate limiter and no registered routes.
- **Core data surfaces:** PostgreSQL primary and replicas, optional PgBouncer, Redis cache/velocity, `pg_audit_db`, `pg_logs_db`, `pg-backup-daemon`.
- **Deployment surface:** `deploy/deploy.env` with compute node arrays, PostgreSQL primary/replicas/PgBouncer, Redis nodes, audit/log nodes, backup node, mTLS PKI, firewall and nginx/PM2 templates; `deploy/backup-daemon` is provisioned from the same config.

The request paths are:

- Payer: browser -> `checkout-front` -> public TLS -> `checkout-back` -> mTLS -> `core-back` `/internal/checkout/*` -> PostgreSQL and, for payment execution, an external gateway through `ApiConsumer`.
- Merchant portal: browser -> `merchant-front` -> public TLS -> `merchant-back` `/api/v1/merchant/*` -> mTLS -> `core-back` `/internal/merchant/*`.
- External merchant server: HTTPS + `Authorization: Bearer pg_live_...` -> `merchant-back` `/api/v1/external/*` -> mTLS -> `core-back` `/internal/merchant/external/*`; core checks the token hash, revocation and optional CIDR allowlist.
- Admin: LAN browser -> LAN-only nginx `:8443` -> `admin-back` `:4101` -> mTLS -> `core-back` `/internal/admin/*`.
- Gateway callback: gateway -> public `checkout-back` `/api/v1/inbound/{gateway}/{env}/{pathToken}` with the raw body -> mTLS -> `core-back` `/internal/checkout/inbound/...`.
- Return URL: payer browser -> `checkout-back` `/api/v1/return/{attemptToken}` -> core inquiry -> status redirect.
- Backups: admin UI -> `admin-back` `/api/v1/admin/system/backups/*` -> core backup router -> mTLS backup daemon `:4090`.

## 6. Operational usage

Typical local verification follows the service READMEs:

```bash
cd core-back
bun run generate-mtls-certs
bun run migrate-generate
bun run migrate-deploy
bun run db-seed
bun run start
```

Each edge backend requires `CORE_BACK_URL` (or `CORE_BACK_URLS`) and its client certificate, key and CA paths. Frontends require their API base URL; the deploy engine injects the admin visibility flags. The full env matrix is generated in `project-design/appendices/env-and-config-matrix.md`; the platform runtime part documents the core groups.

Production operation uses `deploy/deploy.ts` with `deploy/deploy.env`. The engine validates config, plans hosts, provisions storage, deploys core first, then Fake Rails (optional), admin, merchant and checkout, runs verification and prunes old releases inside `deployService()` (not in step 13). The backup daemon is optional but the admin backup write routes return `503 BACKUP_DAEMON_NOT_CONFIGURED` when it is absent; the overview still returns the local catalog.

## 7. Status and deviations

### Implemented

- Seven-service split with database exclusivity and mTLS channel binding.
- PostgreSQL 18 storage engine, schema version 9, migrations, replica reads, Redis cache/velocity, audit and log adapters.
- Dynamic rail engine, transform library, crypto profiles, visible-rails formula and the core API namespaces.
- Merchant onboarding, KYB, AML, disputes, adjustments, cash-outs, reconciliation and ledger scenarios.
- Admin back office and merchant portal foundations, hosted checkout, and optional Fake Rails.
- Durable workers, backup control client and deploy topology arrays.

### Partial

- **Merchant authorization.** Merchant internal routes authenticate and bind to a merchant, but the per-route `requireAuthorities` pattern used by the admin router is not applied; API-token scopes are stored but not enforced per endpoint. `requireMerchantScope` is exported but has no production caller.
- **Approval execution coverage.** Several approval subject types are created but not executable by `executeApprovalSubject`, most notably `APPLICATION`; see `01-core-back/01-api-surface.md`.
- **Horizontal deployment.** Node arrays, least-in-flight pools, PKI SAN generation and rolling batches exist, but a production-shaped multi-host run is not recorded.
- **Backup daemon mTLS.** Core and daemon configuration use different certificate variable names; the daemon can fall back to `127.0.0.1` without mTLS until the deployment writes are aligned.
- **Replica routing.** Only global search and a small set of merchant list routes use `readStore`; most dashboards/lists/exports read the primary.
- **Observability.** No metrics endpoint, tracing, storage health HTTP surface or structured JSON log contract; see `00-platform/04-observability.md`.
- **Schema version at boot.** `ensureSchemaVersion()` exists and requires version 9, but core startup does not call it; only the seeders do.

### Missing / deferred

- Voucher Provider Management System: absent (future part `09-future-and-unimplemented/00-voucher-provider-system.md`).
- Guide v2: absent; the current guide is the implemented 12-book/8-module baseline.
- Google OIDC: `POST /internal/merchant/auth/google` and the edge route return `501 GOOGLE_IDENTITY_NOT_CONFIGURED`.
- `CAPTURE` and `SETTLEMENT_FETCH`: present in the `FlowPhase` database enum but absent from the engine's runtime phase union and flow-provider mapping.
- Storage-plane mTLS: certificates are generated and distributed, but PostgreSQL/Redis configuration does not consume them.
- Voucher, smart-AI voucher onboarding and the full guide authoring pipeline remain design-only.
- Keyset pagination and a comprehensive read-model dashboard path are not implemented.

### Known bugs / risks

- **Code gap:** the `publicRouter` mounted at `/api/public` has no routes; it only installs a 15-requests-per-hour limiter.
- **Code gap:** `payment_attempts` has no `gateway_id` column; the runtime derives the gateway from the pinned version, which is correct for the current model but means any projection that omits the version relation cannot resolve a consumer.
- **Code gap:** the commit-LSN cache used for edge read-your-writes is an in-process map, so a follow-up read routed to another core node does not see it.
- **Documentation gap:** historical counts and claims (13-state lifecycle, 10-phase runtime, 15 ledger templates, 36 transforms) are retained only as historical lineage and are superseded by this document set.
- **Deployment gap:** the backup drill, WAL-G/Barman, secondary mirror and multi-host failover paths have tests but no recorded live run in this verification.
